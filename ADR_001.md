## 1. Contexto y Problema

Tras las entrevistas de validación de mercado, identificamos que los estudiantes de Ciudad Universitaria no tienen una forma centralizada de descubrir y pedir comida a los puntos de venta no oficiales dentro del campus (puestos, cocinas caseras, etc.), y que quienes venden esa comida tampoco tienen un canal digital simple para recibir pedidos y coordinar la entrega (pickup o por estudiante repartidor).

Requerimos una arquitectura web que nos permita desarrollar ágilmente, garantizar el desacoplamiento entre la lógica de negocio (reglas como el perfil dual comprador/vendedor y las estrategias de entrega) y la infraestructura (base de datos, framework web), y facilitar la integración con servicios externos (pasarelas de pago y, a futuro, mapas/geolocalización).

## 2. Decisión

Hemos decidido adoptar las siguientes tecnologías y patrones para el desarrollo del proyecto:

- **Lenguaje y Framework Backend**: Python con FastAPI
- **Framework Frontend**: React (con una librería de mapas tipo Leaflet para el mapa interactivo de CU)
- **Base de Datos Principal**: PostgreSQL (con la extensión PostGIS para las coordenadas de los puntos de venta dentro de CU)
- **Patrón de Arquitectura**: Arquitectura Hexagonal (Puertos y Adaptadores), con la capa de dominio ya implementada de forma pura (ver `src/usuario.py`, `src/domain.py`), sin dependencias de base de datos ni frameworks

### 2.1 Estrategia de entornos: local primero, despliegue después

Por indicación del profesor, el desarrollo inicial del proyecto se hará de forma **local** (en las computadoras de cada integrante), y el despliegue a un entorno público (hosting) se hará en una fase posterior, una vez que el core del sistema esté funcionando.

Para que ese cambio de entorno local → desplegado sea lo más simple posible, mantenemos el mismo stack en ambas etapas (no usamos un motor de base de datos distinto localmente):

- **Local**: PostgreSQL corriendo en un contenedor (Docker/Podman, como ya hicimos en la práctica de Podman), FastAPI con `uvicorn --reload` para desarrollo, y React con su servidor de desarrollo (`npm run dev`).
- **Despliegue (a definir más adelante)**: el mismo backend y frontend, pero corriendo en un proveedor de hosting (por ejemplo Render, Railway o un servidor propio) con una base de datos PostgreSQL administrada. Esta decisión específica de proveedor se documentará en un ADR posterior, una vez que el equipo evalúe costo y facilidad de uso.

Gracias a la Arquitectura Hexagonal, este cambio de entorno no debería tocar la capa de dominio en absoluto — solo los adaptadores de infraestructura (conexión a base de datos, configuración del servidor).

## 3. Alternativas Consideradas

- **Opción A (Descartada)**: Django monolítico — *Motivo de descarte*: dificulta la separación estricta entre frontend y backend que requiere el equipo, y no se alinea bien con el enfoque de capa de dominio aislada (Strategy para métodos de entrega) que ya implementamos y queremos mantener desacoplado del framework web.
- **Opción B (Descartada)**: MySQL — *Motivo de descarte*: no ofrece soporte nativo tan robusto para datos geoespaciales (coordenadas de los puestos de comida en CU) como PostgreSQL con PostGIS, y PostgreSQL maneja mejor tipos de datos JSON nativos para información flexible de productos.

## 4. Consecuencias

- **Positivas**:
  - Separación clara de responsabilidades entre capas (dominio, aplicación, infraestructura).
  - Curva de aprendizaje alineada con la experiencia previa del squad en Python.
  - Facilidad para crear pruebas unitarias sobre el dominio sin depender de la base de datos (como ya se hizo en `tests/test_usuario.py` y `tests/test_domain.py`).
- **Riesgos / Limitaciones**:
  - Mayor tiempo inicial invertido en la configuración de la estructura (scaffolding de FastAPI + React + PostgreSQL).
  - Necesidad de mantener disciplinadamente las reglas de importación entre capas para no romper el aislamiento del dominio.
  - Al usar el mismo motor de base de datos (PostgreSQL) en local y en despliegue, se evita el riesgo de "funciona en mi máquina pero no en producción" por diferencias de motor, aunque sigue pendiente decidir el proveedor de hosting concreto en un ADR futuro.
