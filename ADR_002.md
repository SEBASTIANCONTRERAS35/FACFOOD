# ADR 002: Persistencia, autenticación y estructura del MVP

- **Estado**: Aceptado
- **Fecha**: 2026-10-16
- **Contexto previo**: [ADR 001](ADR_001.md) (FastAPI, React, PostgreSQL + PostGIS, arquitectura hexagonal)

## 1. Contexto

Con el dominio terminado y probado (usuario, entrega, CRM y ERP), toca construir la app: API,
base de datos y pantallas. Dos personas la implementan en paralelo (vistas 01–04 y 05–08) y
el trabajo de cada una no debe depender del de la otra.

## 2. Decisiones

1. **Estructura hexagonal en carpetas.** `backend/app/domain/` (reglas puras), `app/ports/`
   (interfaces de repositorio), `app/adapters/memoria|postgres/` (implementaciones) y una
   carpeta por rebanada de negocio con su router y servicio.
2. **Dos adaptadores de persistencia.**
   - *Memoria*: con los datos de ejemplo; permite correr la API y las pruebas sin base de datos.
   - *PostgreSQL + PostGIS* con **SQLAlchemy 2.0** y migraciones **Alembic**.
   Se elige con `FACFOOD_REPOSITORIO=memoria|postgres`.
3. **Unidad de trabajo.** Cada caso de uso abre una transacción (`with fabrica() as uow`);
   sin `commit()` todo se revierte. El pago bloquea el cupón con `SELECT … FOR UPDATE` para que
   dos pagos simultáneos no usen el mismo cupón de un solo uso (problema de concurrencia del
   material de SCM, "Hot Sale").
4. **Autenticación con JWT** (HS256, 24 h) y contraseñas con bcrypt (Art. 18 LFPDPPP).
   En desarrollo se acepta `X-Usuario-Id` para entrar como un usuario de ejemplo.
5. **Dinero como texto** con 2 decimales en la API y `Decimal` en el backend; el frontend no
   calcula montos de órdenes.
6. **Pago simulado.** La pasarela real será otro adaptador; la factura es la versión sandbox
   del ERP y se genera al pagar.
7. **Frontend**: React 18 + Vite + TypeScript, React Router y Leaflet con OpenStreetMap.
   Los estilos usan los mismos tokens que el Figma.
8. **Contrato compartido** en [docs/CONTRATO.md](docs/CONTRATO.md): tablas, estados, objeto
   Orden y endpoints.

## 3. Alternativas consideradas

- **Solo repositorios de Postgres**: descartado; obliga a tener Docker para cualquier prueba y
  frena a quien no lo tenga instalado.
- **Sesiones en servidor** en lugar de JWT: descartado para el MVP; JWT no requiere estado.
- **Calcular totales en el frontend**: descartado; el servidor dicta precios y montos (regla
  "nunca confiar en el frontend" del ERP).

## 4. Consecuencias

- Cada repositorio existe dos veces (memoria y Postgres). Las pruebas de integración en la CI
  verifican que el de Postgres se comporte igual y que la migración coincida con los modelos.
- La distancia en memoria se calcula con haversine y en Postgres con PostGIS; a escala de CU
  la diferencia es despreciable.
